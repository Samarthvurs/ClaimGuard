# Decisions log

One line per decision: what, and why.

- Repo root is the project folder itself (not a nested `claimguard/` dir): simpler paths, same layout otherwise.
- Python 3.11 venv (3.14 is the system default): best wheel availability for LightGBM, SHAP and Streamlit.
- Default `LLM_MODEL` is `gemini-2.5-flash-lite`: cheapest instruction-following Flash-Lite model on the OpenAI-compatible endpoint; overridable via `.env`.
- Data source: Synthea `master-branch-latest` jar (build d9d07a6, built 2026-08-18), downloaded 2026-10-15, run with `-p 3000 -s 42 -cs 42`, CSV export only. Java 25 was available, so no fallback was needed.
- Synthea output row counts: 3,433 patients (3,000 alive + 433 deceased), 202,990 encounters, 548,888 procedures, 121,980 conditions, 10 payers, 1,014 providers.
- Claims = one row per encounter with a procedure, using the encounter's highest-cost procedure as the principal one; encounters from 2016-01-01 onward only (earlier years are sparse).
- Encounters with payer `NO_INSURANCE` dropped: no claim would be sent to a payer.
- Claims capped at 30,000 by a seeded random sample, to keep training and SHAP fast on a laptop.
- Linked condition = procedure reason, else encounter reason, else first condition recorded at the encounter, else `NONE`.
- `procedure_policy.csv` covers the 150 most frequent procedures; other procedures get a category from the same keyword rules, no prior-auth requirement, and the category's minimum documents.
- Simulated provider "documentation sloppiness" (Beta(1.2, 6) per provider) raises the chance of missing prior auth, missing documents and late filing, so provider history is a real (simulated) signal.
- Simulated coding errors: 4% of claims get the condition of a random other claim; compatibility table = pairs seen at least 5 times before the swaps (rare natural pairs also count as mismatches).
- Label noise flips 5% of labels; a label flipped to denied gets a random reason, one flipped to not denied gets `NONE`.
- History features use a smoothed rate (prior 0.2, weight 5) over strictly earlier service dates; same-day claims do not see each other.
- Every claim gets a note (routine claims too) so the API and dashboard always have a note to show; 12 notes are adversarial.
- Fallback generator writes Synthea-shaped CSVs (same columns) so the builder code is identical for both sources.
- Split: test = latest 20% of service dates; validation = latest 20% of the remaining training period. Models are fit on train only; validation picks hyperparameters, calibration and the threshold.
- Hyperparameter search: small grid (LightGBM 8 combos, logistic regression 3 values of C), chosen by validation PR-AUC.
- Calibration: isotonic fit on the first half of validation and judged on the second half; adopted only if Brier improves by at least 5%.
- Threshold rule: the probability that maximises F1 on the validation slice; stored in the model artifact and metadata (config holds only a fallback).
- Served model is LightGBM (TreeSHAP explanations, non-linear rules); logistic regression is the reported baseline.
- Predicted reason: a multiclass LightGBM trained on denied training claims only; shown only when the claim is flagged as likely denied, otherwise `NONE`.
- SHAP values are summed per raw feature (one-hot columns added back together) so each factor is described in plain language with the claim's actual value.
- Procedure-condition pairing is encoded as log frequency of the pair in the training data (fit inside the pipeline), a time-safe proxy for coding mismatch.
- LLM key not configured tonight (placeholder in `.env`), so the real prompt evaluation was not run; `reports/prompt_eval.*` will be created by `python -m claimguard.llm.eval` once a key is added. The eval CLI writes nothing when no key is set.
- Grounding check normalises whitespace, case, surrounding quotes and a trailing full stop before the substring test; anything else counts as ungrounded.
- Any validation failure (schema, unknown or duplicate item, unanswered item, ungrounded evidence, approve/deny words) triggers one retry with the errors appended to the prompt; a second failure gives `llm_status = "invalid_output"`.
- Grounding rate is measured on the first attempt's output (raw model behaviour before the retry).
- Prompt-eval positive class = item missing; `missing` and `unclear` both count as flagging the item (unclear goes to human review). Injection success = an adversarial note where any truly missing item is reported present.
- Eval set: all 12 adversarial notes plus 88 others stratified by procedure category (seeded).
- The response cache key also includes the attempt number, so a retry is cached separately and reruns resume exactly.
- `/health` is open; every other route needs `X-API-Key` (compared in constant time). Demo protection only.
- Risk bands: LOW_RISK < 0.30 <= NEEDS_REVIEW < 0.60 <= HIGH_RISK on the denial probability; a LOW_RISK claim with missing or unclear documentation (from the LLM check) is lifted to NEEDS_REVIEW.
- Review decisions are `accept_flag`, `dismiss` or `escalate`; "reviewer acceptance rate" = accept_flag / all reviews.
- Demo loader resets the SQLite DB and loads 300 claims sampled (seeded) from the held-out test period so the dashboard never shows training claims. No reviews are pre-filled: review decisions are left to a human.
- When the key is not configured the loader still requests the LLM path, so every assessment records `llm_status = "not_configured"` and the dashboard shows the note; with a key, only the first 20 claims call the LLM (the rest are `skipped`).
- Validation error responses list field locations and messages but never echo input values (so note text never appears in errors or logs).
- Dashboard is a single Streamlit script with a sidebar page selector (simpler to test with AppTest than a multipage app).
- Synthea output depends on the run date and time even with a fixed seed (same jar, a later run gave 203,909 vs 202,990 encounters), so results are reproducible from the saved raw data, not from re-running Synthea. Reported numbers are from the original run.
